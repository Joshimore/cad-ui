# CAD UI — Command & Agent Dashboard

You are working inside **CAD UI** — an isolated, self-contained agentic workspace with a local web UI on top of it. The repo is both the tool and the workspace: team members clone it, launch the UI, and do their work inside this folder. Everything is strictly local: the server binds `127.0.0.1` only, no API keys, no external calls, no CDNs.

## How the pieces interact

```
run_ui.py  ──►  app/main.py (FastAPI, port 8145)  ──►  browser UI (127.0.0.1:8145)
                    │
                    │
                    ├─ app/core/      file layer: config+exclusions, lazy tree scan,
                    │                 markdown render, favorites; search index.py
                    │                 (SQLite FTS5) + tagger.py (heuristic auto-tags)
                    ├─ app/adapters/  auto-detected panels; agents_skills.py watches
                    │                 .claude/agents/*.md and .claude/skills/*/SKILL.md
                    ├─ app/services/  actions: launcher.py (Claude Launch)
                    │  app/adapters/projects.py  team work: Working directory/,
                    │                 projects, tasks, deadlines, timeline
                    └─ app/web/       Jinja2 templates + vanilla JS (no external libs)
```

- **The UI is the eyes, the terminal is the hands.** The web UI never executes arbitrary commands. It reads files, writes its own state (`.cad-ui/state.json` favorites), and performs a **small set of guarded content writes** — create project / task, and edit an open text/markdown document (`POST /api/file/save`) — each behind the same guards: the CSRF header (`security_guard` middleware), a workspace-path check (`resolve_safe` via `guard()`), a type + size limit, and never a command taken from the request. The single command exception is the «>_ Claude» button: `POST /api/claude-launch` opens a terminal in the workspace root running the command from local config (`claude_command`, default `claude`) — never from the HTTP request. Claude Code reads this `CLAUDE.md` on session start automatically, so a session launched from the button already understands the system. Heavier work (creating agents, skills, running code, branded documents) is done by Claude Code in the terminal; the UI picks up file changes on page refresh.
- **Adapters are auto-detected.** If `.claude/agents/` or `.claude/skills/` contain valid files, the UI shows the «Реестр» section (Агенты / Навыки) automatically; if they are absent, the section is hidden. No configuration needed — creating the files IS the configuration.
- **Registry file contracts:** an agent is `.claude/agents/<name>.md` with frontmatter `name`, `description`, `tools`; a skill is `.claude/skills/<skill-name>/SKILL.md` with frontmatter `name`, `description`. The UI reads exactly these fields.
- **Branded documents (bundled `cvd-docs` agent + doc skills).** The repo ships a document-generation capability: the `cvd-docs` agent (`.claude/agents/cvd-docs.md`) drives the bundled `docx`/`pptx`/`pdf`/`xlsx` skills (`.claude/skills/`) to produce on-brand deliverables (Word / PowerPoint / PDF / Excel). It runs **only inside a terminal Claude session** — launch one with the «>_ Claude» button, then ask there (e.g. «сделай брендированный PDF-бриф по задаче …»); the agent generates the file, visually verifies it, and returns the path. The web server never invokes it (UI is eyes, terminal is hands). The brand is defined entirely in the agent's replaceable `=== BRAND STYLE ===` block — swap that block to rebrand, nothing else changes. Put generated deliverables under `Working directory/<project>/output/` — that path is gitignored, so each teammate's documents stay local. Engines: `pdf`/`xlsx` are pure Python; `docx`/`pptx` call Node via `npx` at generation time. The brand fonts (Unbounded + CascadiaMono, both SIL OFL) are bundled at `.claude/assets/fonts/` — beside the agent that uses them, so the whole document-generation module travels as one piece — and resolved from there first, so the brand reproduces on any machine with no network fetch (consistent with the strictly-local rule).
- **Discord statuses (bundled `status` skill).** `.claude/skills/status/` ships a `/status` skill that posts Russian work statuses (day bookends, presence, per-task «Трек», assignment Старт/Итог + branded PDFs) to Discord webhooks. Like `cvd-docs`, it runs **only inside a terminal Claude session** — the FastAPI server adds no routes and makes no outbound calls (UI is eyes, terminal is hands); the skill's `send_status.py` (stdlib `urllib`) does the POSTs. Webhooks are secrets kept in the git-ignored `workspace.config.json` under `status` (never committed); runtime state lives in git-ignored `.cad-ui/status/`. It writes the same `Working directory/<project>/track/…` files the projects adapter reads, so posted tasks surface in the «Проекты» panel automatically. Optional Windows automation (auto day-bookends 09:00/22:00 + 3-hour track drafts) via `register_tasks.ps1` (Task Scheduler). Teammates configure it once per `.claude/skills/status/SETUP.md`; the skill's code is committed, only the webhooks stay local.
- **Work contracts (`Working directory/`):** team projects and tasks live here (created at startup if missing; committed, i.e. shared via git). A project is a folder with `project.md` (frontmatter `name`, `description`, `status`, `created`, optional `due`). A task is `<project>/track/<slug>.md` with frontmatter `name`, `goal`, `state` (active/done), `started`, optional `due`, plus `## Трек (план)` + `## Журнал`; `track/current.txt` names the active task; `track/_draft.md` flags an unsent draft. The «Новый проект»/«Новая задача» buttons write exactly this structure. Deadlines drive the dashboard timeline — `overdue`/`soon` are derived, not stored.
- **Knowledge base (`knowledge-base/`):** trust-rated, version-stamped cards, surfaced by the `knowledge_base` adapter as the «База знаний» panel (`/knowledge`; auto-detected once ≥1 card exists). A card is any `.md` under `knowledge-base/` with frontmatter `title`, `type` (`card`|`anti-pattern`), `trust` (`L0`–`L5`), `version` (the software+version it applies to), optional `tags`, `created`, `stale` (true → flagged outdated). Cards record what works (by trust level); anti-patterns record what doesn't. **Same shared-skeleton model as `Working directory/`:** `knowledge-base/.gitkeep` is committed, the cards are gitignored — each teammate's base stays local. `stale` is a manual flag (a generic tool can't know the "current" version of arbitrary software).
- **Personal vs shared:** `.claude/agents/` and `.claude/skills/` are **committed** (they are the system — including the `status` skill's code). `workspace.config.json` (personal exclusions, `claude_command`, and the Discord `status` webhooks — secrets), `.cad-ui/` (runtime state, incl. `.cad-ui/status/`), `.claude/settings.local.json`, and the *contents* of `Working directory/` and `knowledge-base/` (only their `.gitkeep` is tracked) are **gitignored** — never commit them, never put secrets in tracked files.

## First run — what YOU must initiate

A fresh clone is empty: no venv, no agents, no skills, an almost-blank UI. When a user starts a session in this folder and the environment looks unprovisioned, proactively walk them through bootstrap (ask before each step, don't silently install):

1. **Environment check:** if `.venv/` is missing — the simplest path is `start.bat` (creates the venv, installs deps, launches). Manual equivalent: `python -m venv .venv` → `.venv\Scripts\pip install -r requirements.txt` (needs Python 3.11+ with pip; beware of PATH pythons shipped without pip, e.g. MSYS builds).
2. **Launch the UI:** `start.bat`, or `.venv\Scripts\python run_ui.py` → opens `http://127.0.0.1:8145`. Options: `--port`, `--no-browser`, or an explicit workspace path (default = this folder). To update the system later: `update.bat` (git pull + dependency sync), then restart.
3. **Seed the registry:** the repo ships the `cvd-docs` agent in `.claude/agents/` and the `docx/pptx/pdf/xlsx` skills in `.claude/skills/`, so «Реестр» (Агенты + Навыки) is populated on a fresh clone. Branded-document generation needs the skill engines available in the terminal: `pdf`/`xlsx` are pure Python (pulled in by the venv), `docx`/`pptx` additionally need Node (`npx`) on PATH. If a user works in a domain they don't cover, offer to scaffold a tailored agent/skill from the file contracts above. If the user clears `.claude/agents/` and `.claude/skills/`, the «Реестр» section hides itself automatically.
4. **Orient the user:** point them to the sections — Центр управления (dashboard), Документы (tree + markdown viewer), Недавние, Избранное — and explain that documents they create here appear in the UI immediately.

- Keep it dependency-light: vanilla JS only, no CDN/external assets; new Python deps go to `requirements.txt` with a reason.
- New panels are adapters (`app/adapters/`, pattern: `detect() → parse data → page route + template`), never hardcoded into the core.
- UI style: "engineer's notebook" theme in `app/web/static/style.css` — warm paper background, burnt-orange accent, mono labels. All colors come from the `:root` CSS variables; never hardcode theme colors in templates. Match it. A **dark variant** is defined under `:root[data-theme="dark"]` and toggled from the topbar (preference persists in `localStorage`, defaults to the OS setting, applied pre-paint by an inline script in `base.html`); because every surface reads the `:root` variables, both themes adapt automatically — so keep using `var(--…)` and both stay correct.
- UI text is Russian; code, comments, and this file are English.
